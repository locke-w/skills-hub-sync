## 一、核心逻辑总结

### 1.1 完整工作流程

```
用户触发
    ↓
前置扫描本地资产库（MAX_ID + 属性注册表）
    ↓
动态生成候选画像（30% 现代配额强制）
    ↓
六重正交防御门禁过滤
    ↓
五维深度铸造人物画像卡（D1-D5）
    ↓
提取 15-20 词 IFTS 唯一性指纹序列
    ↓
构建视角 00（Midjourney 写实原片，完整嵌入 IFTS）
    ↓
四大算子微调生成视角 01（3D 模型，100% 继承 IFTS）
    ↓
构建视角 02-10（Gemini 煽情场景）
    ↓
双库落盘（Obsidian 知识库 + 纯图片素材库）
```

### 1.2 十大核心设计原则

1. **零侵权三禁双准原则**: 禁动漫/非中国人/过度磨皮；准年龄质感/平民人设
2. **00→01 微调衍生协议**: 视角 01 依靠 00 通过四大算子精准转化
3. **IFTS 唯一性指纹锁**: 00 与 01 必须 100% 逐字继承核心指纹序列
4. **双引擎职责分工契约**: MJ 专攻 00/01，Gemini 负责 02-10
5. **Full-body 强制契约**: 全身人物必须显式包含 full-body 词条
6. **高信噪比词数熔断**: 50-70 词黄金敏感区间
7. **11 视角零缩水门禁**: 强制完整输出全部 11 个视角
8. **单一职责架构解耦**: 只负责提示词，严禁写文案
9. **30% 现代配额红线**: 强制 30% 为近期去世中年亲人
10. **六重正交防御去重**: 信物/色彩/职业/骨相/ID 全局互斥

### 1.3 关键创新点

#### 创新 1: 00→01 微调衍生协议
- **创新点**: 不是重写两套独立提示词，而是通过四大标准算子精准转化
- **底层原理**: 在潜变量空间实现文本交叉注意力对齐，确保跨视角骨相神态零漂移

#### 创新 2: IFTS 唯一性指纹锁机制
- **创新点**: 15-20 词核心 Token 序列作为单一信任源（SSOT）
- **底层原理**: Assert(IFTS_in_00 == IFTS_in_01) 自动化一致性校验

#### 创新 3: 动态公式驱动去重引擎
- **创新点**: 形式化人物画像生成公式 P = ForgingFormula(K,T,Y,E,V,M,C,A,D)
- **底层原理**: 前置扫描构建属性注册表，六重正交防御实时去重

#### 创新 4: 30% 现代配额强制红线
- **创新点**: 打破"全量高龄祖辈"刻板印象
- **底层原理**: 精准击中"子欲养而亲不待"核心痛点

## 三、问题识别与影响分析

### 3.1 严重问题（Critical）

#### 问题 1: 文档长度过载（124KB / 12 万字符）
- **现象**: SKILL.md 单文件 124KB，包含大量重复强调、示例堆叠
- **影响**: 
  - Claude 每次加载消耗 ~85K tokens（上下文的 42%）
  - 新用户学习曲线陡峭，难以快速定位关键信息
  - 维护成本高，修改一处需同步多处重复内容
- **根本原因**: 缺乏分层文档架构，所有内容平铺在单文件

#### 问题 2: 规则复杂度过高（15 条铁律 × 多重子规则）
- **现象**: 15 条铁律，每条包含 4-8 项子规则，总计 ~80+ 条约束
- **影响**:
  - LLM 容易遗漏关键约束（如 full-body 强制、词数熔断）
  - 调试困难，违规原因难以快速定位
  - 扩展困难，新增规则需考虑与现有 80+ 条的交互
- **根本原因**: 缺乏分层抽象，所有规则平铺，未分核心/扩展

#### 问题 3: 硬编码路径依赖
- **现象**: 15+ 处硬编码绝对路径（如 `/Users/wuyongjia/obsidian-gitee/...`）
- **影响**:
  - 跨用户/跨机器不可移植
  - 团队协作困难，每个成员需手动修改路径
  - 自动化部署受阻
- **根本原因**: 未使用环境变量或相对路径占位符

### 3.2 中等问题（Moderate）

#### 问题 4: 示例过度集中（70% 篇幅为示例）
- **现象**: 厨房外婆、客运老爸、接站父亲三个完整示例占 ~80KB
- **影响**:
  - 核心规则被淹没在大量示例中
  - token 消耗高但信息密度低
  - 修改示例需同步多处（00/01/02-10 每个视角）
- **优化空间**: 示例应外置或折叠

#### 问题 5: 缺乏错误处理与降级策略
- **现象**: 未定义 API 失败、本地库不存在、ID 冲突等异常场景处理
- **影响**:
  - 生产环境鲁棒性不足
  - 用户遇到错误无明确指引
- **优化空间**: 增加异常处理流程图

#### 问题 6: 验证机制缺失
- **现象**: 虽有 Blocker 级缺陷定义，但缺乏自动化验证脚本
- **影响**:
  - 依赖人工检查，易漏检
  - 无法在 CI/CD 中集成质量门禁
- **优化空间**: 提供 prompts.json schema 验证器

### 3.3 轻微问题（Minor）

#### 问题 7: 元数据版本管理缺失
- **现象**: metadata.version 为 "3.8.0"，但无版本变更日志
- **影响**: 升级风险未知，向后兼容性不明确

#### 问题 8: 性能优化空间
- **现象**: 前置扫描全量读取所有 character_profile.md
- **影响**: 资产库增长到 100+ 人物时性能下降
- **优化空间**: 增量索引缓存

### 优化 4: 自动化验证器

**问题**: 无自动化验证，依赖人工检查

**解决方案**:
```javascript
// fullcolor-validator.js
const RULES = {
  L1_CRITICAL: {
    'ifts-consistency': (prompts) => {
      const ifts00 = extractIFTS(prompts['00']);
      const ifts01 = extractIFTS(prompts['01']);
      return ifts00 === ifts01;
    },
    'full-body-presence': (prompts) => {
      const fullBodyViews = ['00-fullbody', '01-fullbody', '07', '08'];
      return fullBodyViews.every(v => 
        prompts[v]?.includes('full-body')
      );
    },
    'completeness-11-views': (prompts) => {
      return Object.keys(prompts).length >= 11;
    }
  }
};

function validate(promptsJson) {
  const violations = [];
  for (const [rule, check] of Object.entries(RULES.L1_CRITICAL)) {
    if (!check(promptsJson)) {
      violations.push({ level: 'BLOCKER', rule });
    }
  }
  return violations;
}
```

**预期收益**:
- 自动检测 Blocker 级缺陷
- CI/CD 集成质量门禁
- 人工检查工作量减少 80%
